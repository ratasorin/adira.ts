# Why Service Risk is slow

This diagnostic describes the implementation **before the independent cost producer was split**. The [split-cost comparison](split-cost-comparison.md) records that implemented follow-up; [bulk reductions and load scheduling](../../../docs/bulk-reductions-and-load-scheduling.md) remain proposals.

At measurement, the Adira demo performed more database work, executed simple reductions through many parent-scoped lookup contexts, and serialized independent dependency loads. Root index lowering addresses account discovery; it does not change those execution strategies. Some of this is the demo's backend modeling, and some is the managed executor's current strategy. It is not an irreducible cost of typed frontend selections or JavaScript scoring.

## Evidence

The full [HTTP comparison](index-lowering-comparison.md) records 951.6 ms median for Adira versus 68.4 ms for the reference. Both score exactly **486 accounts** and return the same 25 selected rows. The risk function is shared JavaScript in [business.ts](../server/clock.ts); the reference does not avoid the application score or paginate before calculating it.

A follow-up [per-command trace](service-risk-profile.json), generated by the [reproducible diagnostic](service-risk-profile.cjs), uses a fresh private medium seed and four sequential direct executor calls per backend/query mode, alternating order after warmups. All twelve calls match the original risk result digest. This is a diagnostic, not another statistically stable HTTP benchmark.

Mean driver command milliseconds, including getMore, grouped by phase:

| Phase                              |                           Current Adira |                                  Reference |
| ---------------------------------- | --------------------------------------: | -----------------------------------------: |
| Accounts and finance               | 342.8, including revenue and line costs | 9.5 accounts + 22.8 revenue; no line costs |
| Ticket counts                      |                                   243.0 |                                       15.8 |
| Late-shipment counts               |                                   237.5 |                                       22.3 |

Reference aggregates overlap through Promise.all, so their driver durations must not be summed as request wall time. Adira uses 18 driver commands and the reference 10. A driver command can contain hundreds of database-side lookup contexts; these are not hundreds of network round trips.

## Independent work bundled into one atomic producer

The [Adira finance producer](../server/accounts/details.adira.ts) declares gross revenue, refunds, revenue order count, and line-item cost in one `provides` block. Its stages contain two independent lookups: Orders for revenue and Lines for cost. Risk needs net revenue, which activates that whole atomic producer, even though risk neither selects nor depends on cost or margin.

The saved explain shows 486 parent outputs for both lookups, with **2,618 order documents and 10,472 line documents examined**. The cost work is unnecessary for this query. The reference explicitly calls `financials(accounts, context, false)` in risk mode; its `includeCost` branch skips Lines entirely.

The existing API can fix this modeling choice: register revenue/refund/count as one producer and cost as a separate producer. Needing net revenue would then leave the cost producer unused. Adira correctly respects the atomic declaration today; it cannot safely split an arbitrary raw block by guessing which stages are independent.

## Parent-scoped evaluation versus bulk grouping

The raw revenue lookup correlates `_id` to `accountId` and groups with `_id: null` inside that account's matched input. For 486 accounts this means 486 separate parent-scoped revenue evaluations. Its indexes already worked before root lowering. The reference instead matches `accountId: { $in: accountIds }` and groups once by `$accountId`.

The same distinction is more expensive in the managed counts. Adira's readable `tickets.count(...)` and `shipments.count(...)` compile through [relatedBatches](../../../packages/backend/read/execute.ts). It sends a literal batch of parents, unwinds it, and executes `$lookup` plus the child reduction for each parent. The requests are batched, but the reductions are still parent-scoped. The reference performs one bulk ticket grouping and one bulk shipment grouping for all candidate IDs.

Preserving per-parent input is necessary for arbitrary native relations containing limits, grouping, windows, and custom transformations. It is unnecessarily general for these particular simple counts. A specialized bulk reduction strategy could optimize eligible built-ins without changing the public query. Custom bulk fetching is already available through `resolveBatch`, as the exposure implementation demonstrates.

## Dependency loads are sequential

The account source registers ticket counts, shipment counts, and exposure as separate `.load(...)` stages. The [application executor](../../../packages/backend/read/execute.ts) awaits each stage before the next. It processes 486 candidates in four application batches of 128/128/128/102 parents. The trace records four aggregate commands for each count and four exposure callbacks; exposure uses eight aggregate/getMore commands.

The reference loads candidate accounts first, then starts finance and service metrics together; service metrics also start tickets, shipments, and exposure together. Its four independent aggregates overlap. `.toApp({ concurrency: 8 })` bounds per-row callback concurrency; it does not parallelize independent load stages or process eight application batches at once.

## Why the index change can also add overhead

The diagnostic includes an `adira-expr-only` query-shape probe. It removes generated ordinary helper predicates next to Adira's null-normalized exact expressions, including inside lookups, while retaining the exact expressions, raw business matches, and current stage placement. It leaves the product code unchanged. This is not the historical compiler and does not isolate root versus child lowering independently.

| Mean duration                     | Index helpers enabled | Expression-only probe |
| --------------------------------- | --------------------: | --------------------: |
| Account/revenue/cost commands     |                 342.8 |                 339.8 |
| Ticket-count commands             |                 243.0 |                 207.0 |
| Shipment-count commands           |                 237.5 |                 222.0 |
| Exposure commands                 |                  50.3 |                  51.5 |
| Complete direct request wall time |                 926.6 |                 873.8 |

The probe reproduces a smaller slowdown, about 6%, mainly in parent-scoped counts. This supports the conclusion that adding helper matches everywhere is not a universal performance improvement: existing foreign join indexes already narrow the child input, and extra predicates/query structure can add costs repeatedly. The new null helper contains an OR branch for legacy BSON undefined, alongside exact residual tests. Identifying the specific MongoDB planning/execution mechanism requires deeper lookup-level profiling. These four-call measurements do **not** fully explain the earlier HTTP run's 17% regression.

## Implications

1. Split the independent line-cost producer so risk does not activate it. This backend modeling change is now [implemented and benchmarked](split-cost-comparison.md).
2. Give eligible native count/sum operations a bulk grouping strategy instead of the generic per-parent strategy. Preserve exact scope/filter/correlation semantics.
3. Allow declared independent, safe loads to overlap. Arbitrary callbacks cannot be reordered merely because Promise.all is faster.
4. Make helper-match placement sensitive to execution context and measured plans, particularly inside already indexed correlated lookups.

The benchmark compares the current generic plan and backend configuration against a manually optimized endpoint. Its gap should guide improvements to those defaults; it does not establish that every Adira backend must pay that overhead.
